# Project FORESIGHT — Demand & Inventory Intelligence

**Client:** NorthBay Living (simulated D2C home & lifestyle brand) · **Engagement:** Zidio Development Data Science Internship

FORESIGHT turns NorthBay's raw sales, inventory, and calendar data into a weekly SKU-level demand
forecast, a transparent stockout/overstock risk score, a planning dashboard, and a scoring API —
so the ops team knows, every week, what to reorder and what to clear.

## The problem

NorthBay stocks ~200 SKUs on gut feel and spreadsheets. They lose money two ways at once:
best-sellers stock out (lost sales) and slow movers pile up (locked cash, eventual markdowns).
Full brief: see `Instructions.pdf` / `Zidio_Project_Data_1_1.pdf` provided by the program (not
included in this repo — see your program materials).

## The data

The raw extracts are **synthetic**, generated by `src/generate_data.py` to match the brief's data
dictionary (`sales_daily`, `sku_master`, `calendar`, `inventory_snapshots`), and are deliberately
imperfect (duplicates, missing values, inconsistent category labels, a few bad rows) so that
cleaning them is a real part of the pipeline, not a formality.

## Setup & run (reproduces every number in this repo)

```bash
python -m venv .venv && source .venv/bin/activate    # optional but recommended
pip install -r requirements.txt

python src/generate_data.py   # -> data/raw/*.csv
python src/pipeline.py        # -> data/processed/analysis_ready.* + reports/data_quality_log.json
python src/eda.py             # -> reports/figures/*.png + reports/eda_stats.json
python src/forecast.py        # -> reports/backtest_results.json + data/processed/forecast_output.*
python src/risk.py            # -> data/processed/risk_scored.*
```

Then, to use the outputs:

```bash
streamlit run app/app.py               # planning dashboard, http://localhost:8501
uvicorn service.main:app --reload --port 8000   # scoring API, http://localhost:8000/docs
```

Everything re-runs end-to-end from raw data with no manual spreadsheet steps, and random seeds are
fixed (`RNG = np.random.default_rng(42)`, `random_state=42` in the model) so results reproduce
exactly.

## Method (Section 07 of the brief, applied)

1. **Frame**: weekly, SKU-level forecast, 6-week horizon, WAPE as the primary metric (bias as a
   secondary check).
2. **Baseline**: seasonal-naive — same ISO week last year, falling back to last month / SKU
   expanding mean for SKUs without a year of history.
3. **Features**: lags (1, 2, 3, 4, 8, 52 weeks), rolling mean/std (4/8/12 weeks), calendar
   (week-of-year sin/cos, weeks-since-launch), promo flag, price, and a category-level rolling
   mean for sparse-history SKUs. All features are built with `.shift()` before any rolling
   window, so no feature can see its own or a future week's value.
4. **Model**: LightGBM (Poisson objective, since demand is a non-negative count).
5. **Backtest**: rolling-origin CV, 5 folds, each fold trained only on weeks strictly before its
   test window, minimum 60 weeks of training history before the first fold.
6. **Evaluate**: model WAPE compared to baseline WAPE per fold and reported honestly — see
   `reports/backtest_results.json` for every fold's numbers, wins and losses alike.
7. **Risk score**: forecast demand over lead time vs. available stock (stockout), and on-hand
   stock vs. an 8-week healthy-cover threshold (overstock) — see `src/risk.py` for the exact
   (simple, auditable) formulas.

## Key assumptions

- The provided extracts are representative of NorthBay's real sales/inventory behaviour (they are
  synthetic, built to mirror one — see Data above).
- "Healthy" stock cover is defined as ≤ 8 weeks of forecast demand on hand; overstock risk scales
  linearly above that.
- A 1-week safety buffer on top of each SKU's lead time is used for the stockout threshold.
- Inventory position is taken from the most recent available weekly snapshot per SKU.

## Known limitations (stated up front, not hidden)

- New SKUs (~12% of the catalog) have too little history for reliable SKU-level lags and lean on
  category-level trends — forecasts for these carry more uncertainty.
- This is a rule-based risk layer by design (Section 08 of the brief calls for transparency over a
  black box) — it prioritises, it does not compute optimal order quantities.
- The scoring service reads from the latest local pipeline run; it is not wired to a live data feed.
